ПО для автоматического UX-аудита веб-сайтов.

## Введение

SiteAudit AI: клиент-серверное приложение для автоматического UX-аудита веб-сайтов. Система принимает ссылку, парсит содержимое страницы, фильтрует данные и формирует структурированный отчёт с помощью LLM.

Backend реализован на C++ и отвечает за основную бизнес-логику: парсинг, обработку данных и взаимодействие с LLM API. Frontend — отдельный слой поверх REST API, отвечающий за ввод ссылки и отображение результатов анализа.

Frontend и backend взаимодействуют через HTTP-запросы: клиент отправляет ссылку, сервер обрабатывает её и возвращает готовый UX-отчёт для отображения пользователю.

## Возможности

### UX-аудит сайта
- Приём ссылки на сайт через веб-интерфейс
- Валидация URL на стороне сервера
- Парсинг содержимого страницы через отдельный JS-скрипт (извлечение DOM-структуры)
- Фильтрация нерелевантных для UX-анализа данных

### AI-анализ
- Формирование промпта на основе распарсенного содержимого
- Отправка запроса к LLM (DeepSeek) через Router AI API
- Получение структурированного JSON-ответа: описание сайта, проблемы, улучшения, сильные стороны
- Оценка сайта по шкале от 1 до 10
- Автоматическая очистка ответа от markdown-форматирования

### Обработка ошибок
- Проверка доступности и корректности переданного URL
- Обработка ошибок парсинга (недоступность сайта, некорректный ответ)
- Обработка ошибок AI-сервиса (отсутствие API-ключа, сетевая ошибка)
- Возврат структурированных JSON-ошибок на фронтенд

### Веб-интерфейс
- Минималистичный фронтенд для ввода ссылки
- Отображение результатов анализа в читаемом виде
- Взаимодействие с backend через Fetch API

## Архитектура

Система построена по модели клиент-серверного приложения с разделением frontend и backend.

### Общая схема

Frontend → REST API → C++ Backend → Node.js Scraper (Playwright) → Router AI (DeepSeek)

### Frontend

Клиентская часть представляет собой веб-интерфейс, взаимодействующий с сервером через Fetch API.

Отправляет POST-запрос с URL сайта на единственный эндпоинт `/analyze` и отображает полученный результат.

### Backend

Backend реализован на C++ с использованием Crow framework. Это HTTP-сервер, который координирует процесс анализа, делегируя отдельные задачи внешним компонентам.

Он отвечает за:
- валидацию входящего URL
- запуск парсинга страницы через отдельный Node.js процесс
- формирование промпта и отправку запроса к LLM
- обработку и очистку ответа AI
- возврат структурированного JSON-результата

### Архитектурный стиль

Backend построен по слоистой архитектуре:

Controller → Service → Scraper / AI Service

- **Controller**: принимает HTTP-запрос, валидирует URL, возвращает результат или ошибку
- **Service (analyze)**: оркестрирует процесс, сначала вызывает парсинг, потом AI-анализ
- **Scraper Service**: запускает Node.js скрипт и получает от него JSON с DOM-структурой
- **AI Service**: формирует промпт, отправляет запрос к LLM через Router AI API, обрабатывает ответ

### Парсинг сайтов

Парсинг выполняется отдельным Node.js скриптом (`scraper.js`) на базе Playwright. Скрипт:

- запускает headless-браузер Chromium
- эмулирует реального пользователя (подмена User-Agent, отключение WebDriver-флага)
- загружает страницу с ожиданием полной отрисовки (включая SPA с `networkidle`)
- выполняет автоматический скроллинг для подгрузки ленивого контента
- обходит DOM и извлекает структурированные данные:
  - заголовки (h1–h6)
  - текстовое содержимое (параграфы)
  - интерактивные элементы (ссылки и кнопки)
  - формы (поля, кнопки отправки, чекбоксы согласий)
- возвращает результат в формате JSON

Backend вызывает скрипт как дочерний процесс через `_popen` и получает данные через stdout.

### AI-интеграция

Для UX-анализа используется модель DeepSeek v3.2 через Router AI API.

- Запросы выполняются через libcurl
- API-ключ передаётся через переменную окружения `ROUTERAI_API_KEY`
- Промпт содержит извлечённую DOM-структуру и инструкции по анализу
- Ответ парсится и очищается от markdown-форматирования перед отправкой на фронтенд

### Поток обработки запроса

Frontend → POST /analyze (URL) → Controller → Analyze Service → Scraper Service → AI Service → Router AI API → Controller → Frontend

Контроллер выполняет:
- валидацию URL
- передачу в сервисный слой
- очистку и упаковку ответа AI
- возврат результата или ошибки

## Особенности реализации

### Парсинг современных сайтов

- Для scraping используется Playwright + Chromium, что позволяет корректно обрабатывать как статические страницы, так и SPA-приложения с динамическим рендерингом контента.
- Реализованы базовые механизмы повышения совместимости с современными сайтами:
  - подмена User-Agent;
  - скрытие navigator.webdriver;
  - автоматический скроллинг страницы для подгрузки lazy-loaded контента.
- Используется fallback между networkidle и domcontentloaded для сайтов с нестабильной сетевой активностью.

### Структурирование данных

- Вместо передачи полного HTML в LLM выполняется предварительное извлечение и структурирование данных страницы.
- Из DOM извлекаются:
  - заголовки;
  - текстовый контент;
  - интерактивные элементы;
  - формы.
- Такой подход уменьшает объём данных, снижает расход токенов и делает AI-анализ стабильнее.

### Архитектура backend

- Backend разделён на отдельные слои:
  - controller;
  - service;
  - scraper service;
  - AI service.
- Scraper вынесен в отдельный Node.js процесс и запускается из backend через _popen, что изолирует scraping-логику от основного сервиса.
- Backend реализован как stateless-сервис: состояние не хранится между запросами.

### AI-интеграция

- Взаимодействие с LLM вынесено в отдельный сервис (ai_service).
- Prompt формируется программно и содержит ограничения на формат ответа:
  - строгий JSON;
  - отсутствие markdown;
  - запрет ложных предположений о содержимом страницы.
- Дополнительно реализована очистка markdown-обёрток, если модель всё же возвращает ответ в формате json.

### Валидация и обработка ошибок

- Проверка URL выполняется через libcurl (curl_url_set), а не через простую regex-валидацию.
- Реализована централизованная система обработки ошибок с HTTP-статусами:
  - 400: ошибки валидации;
  - 502: проблемы scraping;
  - 500: внутренние ошибки сервиса.
- Ошибки возвращаются в структурированном JSON-формате.

### Конфигурация

- Конфиденциальные данные вынесены в переменные окружения:
  - ROUTERAI_API_KEY: API-ключ AI-сервиса.
- Backend поддерживает CORS и многопоточную обработку запросов средствами Crow.

## Установка

### 1. Клонирование репозитория

```
git clone --recursive https://github.com/Timofey10012/siteaudit-ai.git
```
```
cd siteaudit-ai
```

Флаг --recursive нужен для загрузки vcpkg (подключён как submodule).

### 2. Backend (C++)

Требования:
- CMake 3.21+
- Ninja
- MSVC (C++20 compiler)
- Git
- vcpkg (подключён как submodule)
- Node.js LTS
- npm

Примечание: для сборки backend рекомендуется использовать
x64 Native Tools Command Prompt for Visual Studio (MSVC toolchain).

Инициализация vcpkg (из корня проекта):

```
cd vcpkg
bootstrap-vcpkg.bat
cd ..
```

Сборка (из корня проекта):

```
cmake --preset default
```
```
cmake --build --preset default
```

Запуск:

```
build\ai_ux_auditor_backend.exe
```

Сервер запускается на http://localhost:8080.

### 3. Frontend

Frontend является статическим HTML/CSS/JS интерфейсом.

Для запуска достаточно открыть: 
```
frontend\index.html 
```
в браузере.

### 4. Конфигурация окружения

Установить переменные окружения (глобально):
- ROUTERAI_API_KEY: API ключ Router AI

Пример строки подключения есть в .env.example.

### 6. Запуск проекта

- Запустить backend
- Открыть frontend (index.html)
- Ввести URL сайта для анализа

Frontend взаимодействует с backend через HTTP API.

### Примечания

- Проект ориентирован на локальный запуск.
- HTTPS и production deployment не настроены.
- Scraper использует headless Chromium через Playwright.
- Анализ выполняется через LLM API (DeepSeek через Router AI).

## Использование

Приложение представляет собой клиент-серверный сервис для автоматизированного UX анализа сайтов с использованием AI.

После запуска backend и открытия frontend пользователь может:

- ввести URL сайта для анализа;
- дождаться завершения scraping и AI-анализа;
- получить:
  - краткое описание сайта;
  - оценку UX/SEO;
  - список обнаруженных проблем;
  - рекомендации по улучшению;
  - сильные стороны интерфейса и структуры.

## Ограничения и будущие улучшения

Разработка была приостановлена до выхода на production-уровень, поэтому часть решений реализована на базовом уровне. Дальше перечислено, что сейчас упрощено и что осталось бы доработать при продолжении проекта.

### Архитектурные ограничения

- Система работает только в локальном окружении (HTTP, без HTTPS и production-деплоя)
- Scraper реализован как отдельный Node.js процесс, а не как отдельный сервис или библиотека уровня backend
- Нет очередей задач и асинхронного job-менеджмента для обработки анализа
- Отсутствует масштабирование и ограничение параллельных анализов

### Scraping и работа с веб-страницами

- Используется Playwright с headless Chromium без полноценной антидетект-стратегии уровня production
- Обход антибот-защит реализован частично и без гарантии стабильности на всех сайтах
- Эмуляция поведения пользователя упрощена (User-Agent, webdriver flag, viewport)
- Infinite scroll и SPA-обработка реализованы эвристически и могут работать нестабильно на сложных сайтах

### AI-интеграция

- Используется внешний API (RouterAI + DeepSeek), что делает систему зависимой от стороннего сервиса
- Отсутствует кеширование результатов анализа
- Нет контроля стоимости токенов и ограничения глубины контекста
- Промпт-инжиниринг полностью ручной и не адаптивный

### Обработка данных

- Извлечение контента страницы основано на DOM-траверсе и эвристиках, а не на семантическом понимании страницы
- Возможна потеря части информации из-за упрощённой структуры парсинга
- Нет пост-обработки или нормализации данных уровня production NLP pipeline

### Надёжность и эксплуатация

- Scraper запускается как дочерний процесс через stdout без системы очередей или повторных попыток
- Ошибки обрабатываются на уровне статусов, но без сложной системы retry/backoff
- Отсутствует мониторинг, метрики и логирование уровня production

### Возможные улучшения

- Выделение scraper в отдельный сервис с API 
- Введение очередей задач 
- Добавление кеширования результатов AI-анализа
- Улучшение антибот-стратегий и стабилизация scraping логики
- Добавление метрик, логирования и наблюдаемости
